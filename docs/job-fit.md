## 인턴 경험에서 가져온 것

**LS웨어 품질관리팀 인턴: user_reported + 로컬 경험 원장 확인.** 공식 경력증명서를 이번 작업에서 새로 검증한 것은 아닙니다.

| 과거 수행 범위                                                   | 이번 프로젝트에서 바꾼 형태                    | 근거 수준                                      |
| ---------------------------------------------------------------- | ---------------------------------------------- | ---------------------------------------------- |
| Linux TestBed 환경 구성과 설치·기동·접속·기능 확인               | 기동 / HTTP / SQL / 생산실적 기능의 독립 점검  | 경험은 사용자 설명·로컬 원장, 연결은 derived   |
| 패키지·의존성·저장소·방화벽·SELinux·포트 조건을 나누어 실패 재현 | 서비스 중지·포트 오류·모의 DB 권한 거부 실습실 | 실제 인턴 환경을 그대로 재현했다는 주장은 아님 |
| 후속 담당자가 따라갈 수 있는 설치·점검·트러블슈팅 가이드         | 실패 조건·수정 내용·재검증 근거를 묶은 가이드  | 이번 코드·화면·테스트는 verified_local_source  |

인턴 당시 프로덕션 서버 운영, 고객 장애 대응, AI 앱 개발, 검증시간 절감률을 수행했다고 쓰지 않습니다. 내부 환경표·설치 가이드·로그 원본도 포함하지 않았습니다.

## 지원서와 면접에서 설명할 수 있는 문장

> Linux QA에서 설치 성공만으로 점검을 끝내지 않고 기동·접속·기능까지 나누어 확인했던 방식을 웹 앱으로 옮겼습니다. 생산실적 조회가 실패하면 MCP 도구로 실행 상태, HTTP 응답, SQL 조회, 업무 기능을 확인합니다. 실패 근거와 수정 후 결과를 연결하고, 재검증이 끝난 기록만 가이드로 저장하도록 만들었습니다.

이 문장은 프로젝트를 실행하고 코드를 이해한 뒤 본인의 설명으로 다듬어 사용해야 합니다. AI 도구가 작성한 구현을 본인이 전부 단독 작성한 것처럼 설명하지 않습니다. 외부 LLM API 연결은 실제 모델로 점검한 기록을 추가한 뒤 완료 경험으로 설명합니다.

## 면접에서 보여줄 순서

1. 연결 포트 오류 재현 → 실제 리스너와 설정 주소 비교
2. 정상 환경 복구 → 같은 네 항목 재검증 → 해결 기록 저장
3. server/incidents.ts의 완료 조건과 최신 실패 근거 선택
4. server/diagnostics.ts의 실제 MCP 통신과 고정 대상 제약
5. docs/query-plan.json의 SQL 실행계획, tests/backend.test.ts의 검증 기준
6. 실제 LLM 요청 기록이 있으면 모델·시각·도구·토큰을 보여주고, 없으면 미검증이라고 설명
